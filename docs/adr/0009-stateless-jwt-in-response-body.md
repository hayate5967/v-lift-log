# ADR-0009: 認証はステートレスな JWT とし、トークンはレスポンスボディで返す

- ステータス: 採用
- 日付: 2026-08-06

## 背景

第1部の最初の機能として Auth（登録／ログイン／本人確認）を実装するにあたり、
「ログイン状態をどう保持するか」と「トークンをクライアントへどう渡すか」を決める必要があった。

このアプリのクライアントは Web ブラウザだけではない。
[ADR-0002](0002-all-web-device-integration.md) のとおり ESP32 も同じバックエンドを叩く。
デバイスは Cookie を扱えず、API キーを HTTP ヘッダに載せる方式になる。

## 決定

- ログイン状態はサーバー側に持たず、**署名済み JWT を Bearer トークンとして扱う**。
  セッションテーブルは作らない。
- `POST /auth/register` と `POST /auth/login` は**レスポンスボディで token を返す**。
  バックエンドは `Set-Cookie` を発行しない。Cookie に載せるかどうかはフロント側の判断に委ねる。
- ただし `JwtStrategy.validate()` は**毎リクエスト DB でユーザーの実在を確認する**（完全な無状態にはしない）。

## 理由

- **クライアントが2種類あるため、認証の入口を「ヘッダ」に統一できる**。
  ユーザーは `Authorization: Bearer <JWT>`、デバイスは API キー。
  どちらも Cookie に依存しないので、CORS や SameSite の設計が単純になる。
- サーバーがセッションを保持しないため、**DB へのセッション参照が不要**で、
  水平スケールやプロセス再起動でログアウトが起きない。
- `validate()` での DB 確認は 1 クエリのコストを払う代わりに、
  **退会・削除されたユーザーのトークンが期限まで生き続ける問題を防ぐ**。
  ステートレスの利点をほぼ保ったまま、実務上いちばん困る失効ケースだけを塞ぐ折衷案。

## 検討した代替案

- **サーバーサイドセッション（Cookie + セッションテーブル）**:
  失効は即座に効くが、デバイス側が Cookie を扱えないため認証方式が二重になる。
  ソロ開発で持つには複雑すぎる。
- **バックエンドが直接 httpOnly Cookie をセットする**:
  XSS 耐性は上がるが、バックエンドが「ブラウザ用」と「デバイス用」で分岐することになり、
  API の性格が濁る。フロント（Next.js）側で Cookie に詰め替える方が責務が分かれる。
- **リフレッシュトークンの導入**: 失効管理は堅くなるが、トークン2種類＋保存先＋
  ローテーションの実装が必要。今回の規模には過剰と判断し、有効期限 7 日の単一トークンにした。

## 影響

- JWT のペイロードは `{ sub: userId, email }` のみ。
  トークンは署名されているだけで**暗号化されていない**（誰でも中身を読める）ため、
  秘密の情報を入れてはいけない。
- 秘密鍵は `JWT_SECRET`、有効期限は `JWT_EXPIRES_IN`（既定 7 日）で環境変数から与える。
  未設定なら `getOrThrow` で起動時に落とす。
- **ログアウトはクライアント側でトークンを破棄する**だけになる。
  サーバー側で個別のトークンを無効化する手段は無い。
  即時失効が必要になったら、この ADR を置き換えて失効リスト（jti のブラックリスト）を検討する。
- フロント実装時に、受け取った token を httpOnly Cookie に保存する層を Next.js 側に作る
  （docs/design.md 5-1 の「JWTはhttpOnly Cookie推奨」はこの形で満たす）。
