# ADR-0001: バックエンドに NestJS を採用する

- ステータス: 採用
- 日付: 2026-08-04

## 背景

部活トレーニング記録共有アプリのバックエンドを選ぶ必要があった。
このプロジェクトの目的は「簡単に動くものを作る」ことではなく、実務レベルの設計を体得すること。
特にレイヤードアーキテクチャ（Controller / Service / Repository）と DI を、
自己流ではなくフレームワークに強制される形で身につけたい。

## 決定

バックエンドに NestJS (TypeScript) を採用する。

## 理由

- Controller / Service / Repository + DI の構造をフレームワークが強制するため、
  層を飛び越えた実装が自然と書きにくくなる。認可判定を Service に置く方針も守りやすい。
- TypeScript なのでフロントエンド（Next.js）と言語を統一でき、型定義の共有もしやすい。
- `@nestjs/swagger` で OpenAPI を自動生成でき、API 仕様のドキュメント化が追加コストなく済む。
- Jest によるテストが標準構成に含まれ、Service 単体テストと e2e の両方を最初から書ける。
  このアプリで最重要の「認可の境界テスト」を CI に載せる前提が整う。

## 検討した代替案

- **Go**: システムを根っこから学べるが、フロントと別言語になり学習の焦点が分散する。
- **FastAPI (Python)**: Python は既知で新規性が低く、DI やレイヤ構造の強制も弱い。
- **Supabase 等の BaaS**: 認証・API・DB アクセスが自動化されてしまい、
  今回いちばん学びたい部分（認証の仕組み、認可の実装）がブラックボックスになる。

## 影響

- TypeScript でフロントとバックの言語が統一される。
- ボイラープレートは増えるが、それが層構造を意識させる装置として機能する。
- ORM は Prisma を組み合わせる（DB アクセスは Repository/Prisma に集約する）。
