# ADR-0004: デバイス記録の帰属は「セッション」で解決する

- ステータス: 採用
- 日付: 2026-08-04

## 背景

計測デバイスは部内の共有物で、[ADR-0002](0002-all-web-device-integration.md) の構成では
デバイスは「自分が今誰に使われているか」を知らない。
一方でデバイスが送ってくるレップ数・速度は、**特定のユーザーの記録**として保存されなければならない。
デバイス側に人を選ばせる UI（ボタン・画面）を付けるのは、ハードウェアの制約上つらい。

## 決定

`Session` エンティティを導入する。ユーザーが Web で「セッション開始」を行うと、
バックエンドが active なセッションと**そのユーザーの空の Record** を作り、デバイスと本人を紐づける。
デバイスから届いたセットは、このセッションの Record に追記される。

## 理由

- 「誰の記録か」の判断を**デバイスから引き剥がし、認証済みの Web 側に寄せられる**。
  デバイスは自分の API キーで「自分宛の設定」を取りに行くだけでよい。
- セッション開始時に種目・静止時間の閾値・目標レップ・重量・公開先をまとめて決められるので、
  デバイス側に設定 UI が要らない。
- 記録の所有者が最初から確定しているため、認可判定（所有者のみ編集・削除可）が
  手入力の記録とまったく同じ経路で効く。特別扱いが不要。

## 検討した代替案

- **デバイスにユーザー選択 UI を付ける**: ボタンや小型ディスプレイが必要で、
  人数が増えると操作が破綻する。認証もできない。
- **デバイスを個人に固定割り当てする**: 共有物という前提に反する。
- **後からユーザーが記録を手動で紐づける**: 取り違えが起きやすく、手間も増える。

## 影響

- `Session` は `deviceId` / `userId` / `exerciseId` / `recordId` と設定値を持ち、
  `status` は active / ended の 2 状態（docs/design.md 5-3）。
- デバイス向け API は `GET /device/session`（設定取得・ポーリング）と
  `POST /device/sets`（結果送信）の 2 本で足りる。
- active なセッションが無い状態でデバイスがセットを送ってきた場合の扱いを決める必要がある。
