# ADR-0005: 記録の公開範囲は RecordVisibility による多対多で表現する

- ステータス: 採用
- 日付: 2026-08-04

## 背景

部員は複数のグループに同時所属できる。記録ごとに「どこまで見せるか」を選べる必要があり、
「自分だけ」「このグループだけ」「複数のグループに同時公開」のすべてを表現しなければならない。
非機能要件では「閲覧権限のない記録は絶対に見えない」ことが最重要とされている。

## 決定

`Record` と `Group` の間に中間テーブル `RecordVisibility`（`recordId`, `groupId`）を置き、多対多で表現する。
**RecordVisibility の行が1つも無い記録＝非公開（自分だけ）** とする。

ユーザー U が記録 R を閲覧できる条件は次のいずれか:
1. `R.userId == U.id`（本人）
2. R の RecordVisibility の `groupId` が、U の所属グループに含まれる

編集・削除は所有者のみ。

## 理由

- 「複数グループへの同時公開」を追加のフラグや列挙型なしに素直に表現できる。
- 「行が無い = 非公開」を既定にすることで、**公開の指定を忘れたときに安全側に倒れる**。
  公開範囲の設定漏れが情報漏洩にならない。
- 公開範囲を `public` / `private` のような列挙型で持つ設計に比べ、
  グループが増えてもスキーマ変更が要らない。
- 認可判定が「所属グループ集合との積を取る」という単一のクエリに落ちるため、
  判定ロジックを Service 層 1 か所にまとめやすくテストしやすい。

## 検討した代替案

- **Record に visibility 列挙型（private/group/public）を持たせる**:
  複数グループへの同時公開が表現できない。
- **グループを階層構造にして継承させる**: 部活単位のフラットな構造で足りるのに複雑さだけが増える。

## 影響

- `RecordVisibility` に `@@unique([recordId, groupId])` と `@@index([groupId])` を張る
  （同じ組み合わせの重複防止と、グループ単位のフィード取得のため）。
- フィード取得は「自分の記録」と「所属グループに公開された記録」の和集合になる。
  ページング（limit / cursor）と併せて性能を確認すること。
- **この認可ロジックは必ずテストする**。「閲覧権限のない記録が見えないこと」
  「本人以外が編集・削除できないこと」は CI の必須項目（AGENTS.md）。
